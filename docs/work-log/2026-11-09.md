# X-002 · 보호 대상이 있는 Codex 실행 보류

작업 기준은 `feat/t-011-feature-sessions`의 `bd1b72f`이다. 10월 12일 결과 기록 이후 해당 브랜치에는 커밋 작성 규칙만 추가됐다. 실제 저장소와 개발 중인 Codex의 설치·권한은 보존하고 독립 사본 `spike/x-002-read-evidence`에서 개발했다.

정상적으로 저장된 요청과 DB 쓰기 실패 후 남은 표식은 재시작 뒤에도 보류한다. 디스크 오류로 첫 표식조차 기록할 수 없으면 현재 프로세스에서만 보류하고 앱을 닫기 전에 다시 저장하라고 표시한다. 이 상태에서는 재시작 후 보류를 보장할 수 없다.

## ORBIT에서 재현

1. 비관리자 PowerShell에서 이 개발 사본의 루트로 이동한다. 아래 명령은 기존 ORBIT 프로필과 분리된 시험 프로필 및 빈 프로젝트를 준비한다. 실제 설치본의 앱 데이터를 열 필요가 없다.

   ```powershell
   $trial = New-Item -ItemType Directory -Path (Join-Path $env:TEMP ('orbit-manual-' + [guid]::NewGuid().ToString('N')))
   $project = New-Item -ItemType Directory -Path (Join-Path $trial.FullName 'project')
   [IO.File]::WriteAllText((Join-Path $project.FullName 'protected.txt'), [guid]::NewGuid().ToString('N'))
   [IO.File]::WriteAllText((Join-Path $project.FullName 'allowed.txt'), [guid]::NewGuid().ToString('N'))
   $profilePath = Join-Path $trial.FullName 'profile'
   $project.FullName
   npm.cmd start -- "--user-data-dir=$profilePath"
   ```

2. **프로젝트 폴더 선택**에서 출력된 project 폴더를 고르고 **이 프로젝트로 시작 → 고급 보호 설정**을 연다. `protected.txt` 한 줄을 입력하고 읽기·수정·삭제를 선택한 뒤 **보호 요청 저장**을 누른다.
3. 화면의 실행 보류 사유와 대상 프로젝트를 확인한다. Codex 연결 준비 확인이나 대화를 시도해도 로컬 제어부가 시작을 보류한다. 다른 프로젝트에서도 절대 경로로 접근할 수 있어 저장된 요청이 있는 동안 ORBIT 전체에 적용한다.
4. 앱을 닫았다가 같은 `$profilePath`로 다시 열어 보류 사유와 저장한 경로가 남는지 확인한다. 시험을 마치면 해당 프로젝트에서 경로를 비우고 저장한다. 앱 종료 뒤 위 명령이 새로 만든 `$trial.FullName` 폴더를 탐색기에서 확인해 지울 수 있다.

## 보호 시험 재개 조건

동일 소스로 만든 공개 신뢰 서명본과 독립 검토한 서명본의 SHA-256 또는 기존 정책으로 helper가 실행되는 별도 Windows 시험 환경이 필요하다. 서명본은 시작 정책을 충족하기 위한 수단이며 DLL 초기화 원인은 계속 조사 대상이다. 자세한 명령과 복구는 [현재 실행 방법](../../experiments/x-002-file-access/README.md)에 있다.

실제 Codex 연결 전에는 같은 형제 파일에 사용자 읽기 2건, 제한 직접·자식 각각 허용값 일치와 보호 오류 5를 관측해야 한다. 이어서 각 역할의 허용 쓰기·삭제 효과, 보호 쓰기·삭제 오류 5, 해시 보존, 정상 종료와 중단 뒤 Job·desktop 정리 및 ACL 복원을 확인한다.

이 조건이 충족된 뒤에만 별도 임시 프로젝트의 보호된 PTY 실행을 연결한다. 그 실행의 CLI 시작 헤더와 선택 폴더를 대조하고 `현재 폴더에서 상대 경로 allowed.txt를 읽고 파일에 적힌 식별값만 답해 줘.`로 시험한다. 입력에 기대값을 넣지 않고 허용 응답을 로컬의 기대값과 대조한다. 보호 파일 검사는 파일 내용 출력 없이 실제 열기 오류를 수집한다. 일반 모드 재시도, AI 거절 문장, 양쪽 쓰기가 모두 막히는 읽기 전용 모드는 판정 근거에서 제외한다.

## 22:33 KST · Windows VM 준비 상태 재확인

일반 Windows 사용자로 `prepare-host.ps1 -Step VerifyHost`를 실행했다. Windows 11 Home에서 VirtualBox 미설치, WHP 비활성(상태 2), `PendingFileRenameOperations` 대기를 관측했고 `readyForVmConfiguration=false`였다. 확인한 VM 등록·설치 위치와 다운로드·VM 폴더에 Windows 게스트나 설치 ISO가 없었다. 사용자도 이전 다운로드 외에는 따로 확보한 것이 없다고 확인했다. Smart App Control과 Defender 실시간 보호는 켜져 있었다. 호스트 설치, 기능 변경, 재부팅, ACL 시험을 실행하지 않았다.

보관된 VirtualBox 7.2.20 설치 EXE와 x64 MSI의 Oracle 서명이 유효하고 SHA-256이 기존 기록과 일치했다. MSI의 설치 경로 검사 및 네트워크 구성 작업이 기본 설치에도 예약된다. 해당 버전의 자동 재부팅 제어와 고정 임시 파일 처리는 검토가 남아 있어 자동 설치를 보류한다. 사용자는 Windows 11 Enterprise **x64** 평가판 등록·다운로드와 편한 시점의 Windows 다시 시작을 직접 진행한다. 이후 ISO 경로로 이미지 무결성을 확인하고 호스트를 다시 조회해야 한다. [Microsoft 평가 센터](https://www.microsoft.com/en-us/evalcenter/evaluate-windows-11-enterprise) · [기존 설치 검토](../../experiments/x-002-file-access/vm/README.md)

게스트 전달용 읽기 전용 데이터 ISO `.runtime/vm/guest-media-7e57a6c/ORBIT-X002-tests.iso`를 준비했다. `run.ps1`, `FileAccessProbe.cs`, `verify-report.mjs` 세 파일을 다시 읽어 원본과 바이트 단위로 대조하고 Windows용 Joliet 디렉터리를 확인했다. ISO SHA-256은 `093e7855bb041c6c9ef918b98d8d8230f4d9a4cd3204b46260e4aa348ad7cf2d`이다. Windows 설치 미디어는 별도로 필요하다. 게스트 부팅 후 이 매체를 연결하고 일반 사용자 PowerShell에서 가상 CD의 `run.ps1`을 실행한다. 게스트 정책이 실행을 보류하면 그대로 기록한다. 이번에는 게스트가 없어 사용자·제한 프로세스·자식의 비교, 수정·삭제, 실제 Codex의 작업 경로와 종료 후 복원은 모두 게스트 미검증으로 남겼다.
