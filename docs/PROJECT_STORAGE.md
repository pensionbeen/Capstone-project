# 프로젝트 저장·복원

T-005 기록은 **WL-20261005-01** 및 `ee303624376717c7e17e31038af6a62f93d11b96`을 따른다. T-006은 **WL-20261005-02**, T-007/v3의 구현·검사는 **WL-20261006-01** 및 재개 기록 **WL-20261011-01**을 따른다. [검토 대조표](reviews/2026-10-11-gemini.md).

## 사용 방법과 저장 범위

T-008은 v3를 유지하면서 일반 편집 저장 시 기존 기능 버전·검증 기록을 대조한다. 조건·내용을 같은 버전으로 덮거나 버전을 되돌릴 수 없고, 살아 있는 기능의 검증 기록을 수정·삭제할 수 없다. 새 검증은 현재 버전에 연결한다. 백업 복원은 기존의 안전 사본·전체 복원 경로를 유지한다. [검증·진행률 규칙](VERIFICATION.md).

1. 실제 폴더를 선택한다. 다른 프로젝트에서 작성 중이면 변경을 확정한 뒤에만 저장한다. 취소하면 기존 선택을 유지한다.
2. 프로젝트 이름을 입력하고 **이 프로젝트로 시작**을 누른다. 저장 성공 후 다음 화면으로 이동한다. 실패하면 입력과 이전 저장 내용을 유지한다.
3. 앱을 종료하고 다시 열면 이름·폴더·같은 프로젝트 ID·마지막 선택을 복원한다. 저장된 프로젝트 목록에서 다시 고를 수도 있다. AI는 자동 실행하지 않는다.
4. 프로젝트 선택 화면의 **프로젝트 목록 백업·복원**에서 현재 목록을 백업한다. 사본을 골라 복원하면 네이티브 확인 창을 띄우고, 현재 목록을 먼저 별도 백업한 뒤 적용한다.

저장 대상은 프로젝트 ID·이름·실제 폴더 경로·등록/갱신 시각·마지막 선택과 프로젝트별 기능 묶음/말단·선행 관계·관련 상대 경로·버전별 검증 기록이다. **프로젝트 소스 파일, 요구분석·대화/실행 이력, AI 로그인 정보, 보호 정책은 포함하지 않는다.** 예시 프로젝트도 저장하지 않는다. 대화/활동 이력은 T-012 후속이다. 폴더가 사라져도 저장 항목을 삭제하지 않으며 선택/실행 때 오류를 표시한다.

## 저장 구조와 실행 경계

- Electron의 `app.getPath('userData')/orbit-data/projects.sqlite`에 저장한다. 백업은 같은 위치의 `backups/`이며 화면에서 실제 경로를 확인한다. 기본 사용자 데이터 위치는 프로젝트 저장소와 분리된다. 검사만 고유 `.runtime` 프로필을 사용했다.
- 추가 DB 패키지 없이 `node:sqlite`를 사용한다. 실제 Electron 44.5.1의 Node 24.21.0·SQLite 3.53.4, 시스템 Node 24.15.0·SQLite 3.51.3에서 확인했다. Node SQLite API는 공식 문서의 Release candidate 단계이며 검증한 조합 밖의 호환성을 보장하지 않는다.
- `application_id=0x4f524254`, 현재 `user_version=3`. v1에는 `projects`와 단일 `app_state`, v2에는 `features`, `feature_dependencies`, `verifications`, `verification_criteria`가 추가되며 v3에는 `feature_paths`가 추가된다. 프로젝트 ID 복합 외래키로 다른 프로젝트 기능을 연결할 수 없게 하고 SQL 제약과 서버 검사를 함께 사용한다. 값을 SQL 문자열에 합치지 않고 매개변수로 전달한다.
- 단일 앱 인스턴스가 저장 연결을 소유한다. `DELETE` 저널·`FULL` 동기화·250ms 잠금 대기·확장 로딩 차단·`trusted_schema=OFF`를 사용한다. 이 규모에서 WAL의 동시 읽기 이점보다 파일/복구 경로 단순화를 택했다.
- 프로젝트 100개, 경로 4,096자·이름 80자, 직렬화한 목록 512 KiB, 입력 DB/사본 16 MiB, 완료된 백업 20개 한도다. 이전 메모리 등록의 16개 초과 제거를 영구 삭제로 옮기지 않았다. 한도 초과는 기존 데이터를 보존하고 거부한다.
- native 폴더 창은 main의 임시 후보 ID만 발급한다. 사용자 확정 때 실제 경로를 정규화하고 등록+선택을 하나의 트랜잭션(함께 성공하거나 함께 취소하는 저장 단위)으로 처리한다. 이름+선택도 같은 단위다. commit 뒤에만 검사된 메모리 목록과 화면을 바꾼다.
- 기존 인증 REST의 프로젝트 조회는 `storage: 'sqlite'`, `activeProjectId`를 반환한다. 시작 실패는 `storage: 'unavailable'`과 안내를 반환하며 빈 저장소로 성공 처리하지 않는다. 이름/선택/백업/복원은 main의 고정 IPC 함수이며 정확한 창·프레임·인자·ID·이름을 검사한다. renderer는 DB 경로·SQL·백업 파일명을 지정하지 못한다.
- AI 실행·정리 미확인·종료·다른 폴더/복원 창·HTTP 전달 중인 AI 변경 요청이 있으면 저장 전환을 차단한다. 복원 확인 중 새 submit을 받지 않는다. 현재 실행은 영구 저장하지 않고 성공한 복원 뒤에만 메모리 세션을 초기화한다.

## 초기화·백업·실패 보존

기존 파일은 쓰기 전에 읽기 전용으로 앱 ID·버전·정확한 스키마·무결성·외래키·필드/목록 한도를 검사한다. 새 DB는 v3로 만들며 기존 v1/v2는 변환 전에 `VACUUM INTO`로 검사 가능한 안전 사본을 만든 뒤 트랜잭션으로 v3 변환·버전 변경을 수행한다. 변환 실패 시 트랜잭션을 되돌리고 사본을 남겨 재시도할 수 있다. 미래 버전·외부 DB·손상/변조 DB는 원본을 보존하고 거절한다.

새 DB는 고유 `.initializing` 파일에서 생성·commit·검사·디스크 반영 뒤 하드 링크로 덮어쓰기 없이 확정한다. 첫 생성/commit 실패의 미완성 파일은 보존하고 다음 시작에서는 새 시도를 할 수 있다. SQLite가 열린 실제 DB 파일을 그대로 복사하지 않는다.

백업은 `VACUUM INTO`로 고유 `.partial` 사본을 만들고 읽기 전용 검사·파일 동기화 후 완료 이름으로 확정한다. 실패한 partial은 정상 목록과 20개 한도에 포함하지 않는다. 완료 사본은 자동 삭제/덮어쓰기하지 않는다. 한도에 이르면 사용자가 표시된 백업 폴더에서 사본을 별도로 보관한 뒤 정리해야 한다. 초기화와 백업은 하드 링크를 지원하는 로컬 파일 시스템을 전제로 하며 미지원이면 성공으로 처리하지 않는다.

복원할 사본은 한 읽기 트랜잭션에서 검사한 행을 메모리에 가져온다. 검사 후 파일을 다시 열어 다른 내용을 읽지 않는다. 현재 상태 백업이 실패하면 적용하지 않는다. 검증한 프로젝트/선택/기능/관계/경로/검증 기록을 한 트랜잭션으로 교체하며, 실패하면 이전 데이터와 목록을 유지한다. 성공 응답에 확정된 목록을 포함해 후속 조회 실패 때문에 화면만 이전 상태로 남지 않게 했다. 처리 중 취소·닫기·Escape는 막는다.

기능 모델은 최대 100개, 의존 500개, 검증 1,000개, 전체 JSON 2MiB로 제한한다. 묶음은 완료 조건을 직접 갖지 않고 말단 기능은 하나 이상을 가진다. 계층·선행 관계의 순환/자기 참조를 거부하고, 검증은 같은 프로젝트 기능과 revision을 참조한다. 기능 내용·조건·선행 관계·관련 경로 변경 시 revision을 올려 이전 검증을 기록으로 보존한다. 상위 묶음 이동만으로는 버전을 올리지 않는다. 백업에는 기능 모델과 검증 기록이 포함되고 이전 v1 사본은 기능 목록이 비어 있는 것으로, v2 사본은 관련 경로가 없는 것으로 읽힌다. v1/v2/v3 사본을 검사해 복원한다. 관련 경로는 기능당 20개·각 1,000자이며 루트 기준 상대 경로만 저장한다. 없는 경로는 연결 정보를 유지하고 실제 열기 때 오류를 알린다.

**T-007은 묶음/말단·선행 관계·관련 경로 편집과 v3 변환까지 구현했다.** 손상된 실제 DB 자동 교체, 강제 충돌/전원 장애 내구성·다른 PC·패키징은 후속이다. 손상 시 저장 차단 안내와 원본을 유지한다. 이번 결과를 모든 디스크/OS 장애에서 데이터가 보존된다는 보장으로 확대하지 않는다.
