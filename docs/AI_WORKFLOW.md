## 역할과 수정 담당

| 담당 | 역할 | 기본 권한 |
|---|---|---|
| Codex | 설계 정리·구현·테스트·수정·통합·기록 취합 | 지정 브랜치·범위만 수정 |
| Gemini | 독립 설계/코드 검토·대안·테스트 누락 확인 | 읽기 전용. 개발과 의견 반영은 Codex |
| 사용자 | 요구·우선순위·핵심 범위 변경·중요 위험 수용·최종 결과 확인 | 학교 기준·기기/계정·시연/제출 결정 |

같은 작업 폴더에서는 한 번에 한 AI만 파일을 수정한다. 별도 CLI의 지시·대화·실행 결과는 자동 공유되지 않는다. 다른 브랜치라도 같은 폴더의 동시 수정은 금지한다. 별도 worktree(하나의 저장소 이력을 별도 작업 폴더에서 쓰는 기능)는 독립 작업에만 고려하며 취합 담당이 통합한다. npm CLI는 사용자 지시대로 `codex.cmd`·`gemini.cmd`를 사용한다. 후속 확인된 **Antigravity CLI의 agy.exe는 별도 프로그램**이며 버전·설정·인증 근거를 섞지 않는다.

사용자가 AI 사용을 전제로 개발한다는 점을 반영한다. AI가 초안을 빠르게 만들더라도 사람이 검토·환경 재현·기기 연결·시연 판단하는 시간은 별도로 필요하다.

## 모델과 추론 수준

모델은 사용하는 엔진의 종류, 추론 수준은 답을 검토하는 깊이/시간에 대한 설정이다. 모델 이름을 문서에 적는 것은 현재 실행 세션의 모델을 바꾸는 동작이 아니다. 높은 설정도 검증 증거가 되지 않는다.

| 작업 | 사용자 지정 운영 기준 | 이유·상향 조건 |
|---|---|---|
| 중요한 구조·권한 경계·OS 보안 구현 | **Codex에서 사용 가능한 Astra 최고 수준** 우선 | 보안 경계·대안·실패 영향을 함께 분석. 단일 어려운 문제는 Max, 독립 구현은 별도 Codex 담당으로 분리. 독립 검토는 Gemini |
| 일반 기능 구현·테스트·수정 | **GPT-6.1 Sol / High** 기본 | 반복 구현의 품질·비용 균형. 요구 충돌·재현 안 되는 오류·같은 실패 반복·보안/DB 손상 가능성이 있으면 Astra 상향 |
| 어려운 오류 분석 | Astra의 사용 가능한 최고 수준 | 먼저 최소 재현·로그·실패 조건 확보. 설정만 올리며 같은 시도를 반복하지 않음 |
| 독립 설계·코드 검토 | 실제 선택 가능한 **Gemini Pro 계열** | 다른 관점의 대안·누락 확인. 정확한 모델 ID·프리뷰 여부·한도 기록 |
| 작은 문서/기록 정리 | 현재 확인된 모델 또는 Sol / High | 신규 구조/핵심 범위 판단이 섞이면 위 기준 적용 |

2026-10-03 사용자 후속 결정: Gemini Pro 사용량에 여유가 있으므로 검증에 적극 활용한다. 중요한 변경의 독립 검토·실패 원인·테스트 누락 확인에 우선 사용하고, 서로 다른 관점이 필요하면 검토를 나눈다. 이는 계정의 잔여량을 직접 측정했다는 뜻이 아니다. Pro 모델 확인·읽기 전용 경계·결과 대조 규칙은 유지하며 Flash로 조용히 대체하지 않는다.

Astra 사용 가능 여부와 지원 설정은 계정·앱·CLI·배포 상태에 따라 확인한다. API 모델 문서는 Astra와 GPT-6.1 Sol에 `low/medium/high/xhigh/max`를 명시하지만, Codex/ChatGPT의 Ultra 운영 방식과 같은 것으로 간주하지 않는다. [Astra API](https://developers.openai.com/api/docs/models/gpt-6-astra), [Sol API](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

공식 제품 문서에서 Max는 한 어려운 작업에 더 깊은 추론, Ultra는 나눌 수 있는 작업에 하위 에이전트를 활용하는 방식으로 설명한다. CLI 모델 목록·실제 실행 표시와 결과를 함께 확인한다. X-001에서 내장 보조 에이전트에 Astra/Ultra를 요청해 응답을 회수했으나 실제 실행 모델을 독립 표시로 확인하지 못했다. 이를 설치된 CLI의 Max/Ultra 지원 증거로 쓰지 않는다. [공식 모델 안내](https://learn.chatgpt.com/docs/models)

**현재 확인 수준:** 사용자는 Codex와 Gemini를 설치하고 로그인했다고 확인했다. 이는 사용자 보고이며 현재 샌드박스에서의 CLI 실행·인증 검증과 구분한다. 실제 경로/버전 조사·접근 한계는 [T-001 환경 결과](ENVIRONMENT.md)를 따른다. Gemini/GPT Pro 계열·약 16만원은 사용자 표현이고 정확한 요금제·포함 모델·CLI 사용 한도·별도 API 과금은 미확인이다. 금액으로 특정 플랜을 단정하거나 자동 구매하지 않는다. 이번 도구 세션의 제품은 Codex이며 세부 실행 모델·추론 수준은 신뢰할 수 있는 실제 표시를 확보하지 못했으므로 기록에 ‘미확인’을 쓴다.

### 주담당이 보조 호출을 운영한다

최신 사용자 결정으로 작업마다 수동 모델 전환·Gemini 대화 복사를 요구하던 방식을 바꾼다. 주담당 Codex가 작업 ID·난이도·위험·독립 검토 필요성을 판단하고 호출·결과 회수·반영 기록을 맡는다. 이 규칙은 모델 가용성이나 실행 권한을 새로 부여하지 않는다.

1. 주담당은 일반 작업인지, 구조/OS 보안/데이터 손상/인증 경계/어려운 오류/최종 검토인지 분류하고 선택 이유를 남긴다. 독립 검토로 나눌 이점이 있을 때만 Ultra를 검토한다.
2. 같은 환경의 Codex 모델 목록에서 gpt-6.1-sol/High 또는 gpt-6-astra의 지원 수준을 확인한다. 목록은 실제 계정 호출 성공과 구분한다. 지정 모델/수준이 없거나 한도가 막히면 알리고 중요한 작업을 다른 모델로 조용히 넘기지 않는다.
3. 사용 가능한 내장 보조 에이전트 도구 또는 검증한 CLI 호출을 사용한다. 보조 도구의 요청 모델 매개변수와 응답의 실제 모델 정보는 별도 필드다. 요청 수락·AI 자기 보고만으로 실제 모델을 확정하지 않는다.
4. 검토는 기본 읽기 전용이며 주담당이 전달문을 만든다. Gemini는 명시적인 Pro 후보와 제한된 실행 설정으로 호출하고 결과를 회수한다. 보조 CLI끼리 대화가 공유된다고 가정하지 않는다.
5. 응답·종료 코드·도구 활동·모델 표시·파일 무변경을 검사한다. 불일치/메타데이터 부재는 사용 보류, 오류·제약은 사용자에게 알린다. 검토 채택 여부는 실제 요구·코드·재현 근거로 판단한다.

현재 실행 도구는 [X-001 실행기](../experiments/x-001-ai-terminal/README.md), 실제 확인 수준은 [실험 보고](experiments/X-001.md)다. 17:39 KST 사용자 실행 결과에서 Codex 실제 응답과 CLI 모델 목록을 확인했다. 기존 JSON 채널은 실행 모델/추론을 표시하지 않아 미확인이고, 텍스트 헤더를 회수하는 수정본의 서비스 검증은 대기다. 도구 활동이 출력되지 않았다는 사실을 무도구 실행 증명으로 쓰지 않는다. 현재 도구 세션은 설치 폴더 접근 거부가 계속된다.

실행기는 일반 작업에 Sol/High, 중요한 작업에 Astra를 선택한다. **응답 관측·CLI가 확정한 설정·원격 모델 신원 증명은 서로 다르다.** Codex 첫 설정 헤더와 요청값/읽기 전용 권한을 대조하고 모델 변경 알림이면 거절한다. 이름 자기 보고는 쓰지 않는다. 현재는 CLI 설정까지만 확인 가능한 설계이며 원격 신원 증명을 제공하지 않는다.

기존 Gemini CLI 어댑터의 후보는 gemini-3.1-pro-preview다. init.model은 설정값, 최종 모델별 사용 통계는 CLI 관측 근거다. 다른 모델이면 결과를 버리고 알린다. 사용자 후속 증거는 **Antigravity 1.1.10 / Google AI Pro / Gemini 3.1 Pro (High)**다. 기존 Google 로그인을 사용하며 Gemini CLI의 설정을 이 계정 인증 증거로 대입하지 않는다. Antigravity 후보 식별자·옵션은 설치 버전 도움말/목록을 확인한 뒤 확정한다. 현재 Gemini CLI 어댑터를 agy.exe에 그대로 적용하거나 재로그인/API 전환을 요구하지 않는다.

### 현재 대화 모델·쓰기 담당 인계

**최신 병렬 운영:** 아래 초기 단일 폴더 인계 규칙의 ‘주담당 수정 중지’는 같은 작업 폴더를 넘기는 경우입니다. 서로 다른 worktree에서는 총괄과 각 Codex가 지정 파일을 병렬 수정할 수 있습니다. 보조는 결과·검사·파일 목록을 보고하고 총괄의 사용자 안내 후 자기 브랜치에 로컬 커밋합니다. 총괄은 수정 종료를 확인한 뒤 커밋을 회수하고 충돌·공통 계약·통합 검사를 책임집니다. 보조는 push·main 병합·노션·공통 기록을 변경하지 않습니다. Gemini의 기존 deny 환경을 쓰기용으로 바꾸지 않습니다. 이전 Astra 검토는 과거 근거로 보존하며 새 독립 검토는 Gemini가 맡습니다.

향후 일반 구현을 별도 Sol/High 보조 작업자에게 맡길 때는 주담당이 기준 커밋·허용 파일·완료/검증 조건을 넘기고 **자신의 파일 수정을 중지**한다. 정상 응답과 변경/검증을 회수한 뒤 수정권을 되찾는다. 응답 실패·시간 초과 때는 작업자의 종료와 쓰기 중단을 확인하고 실제 변경분·검증 여부를 대조해 미완료 인계를 기록한 뒤 회수한다. 종료나 쓰기 중단이 불확실하면 같은 폴더 수정을 재개하지 않는다. 재개는 기록된 작업자 PID·생성시각과 관측 후손의 종료 및 쓰기 중단을 확인하고 변경분을 대조한 뒤에만 허용한다. 잠금이 남았다면 원본을 보존해 정리하고 그 근거를 기록한다. 확인할 수 없으면 사용자에게 남은 확인 항목을 알리며, 잠금 삭제나 이름별 일괄 종료로 해제하지 않는다. 같은 폴더에서 두 AI의 동시 수정은 금지한다. 읽기 전용 Astra/Gemini 검토는 역할을 명시해 병행할 수 있다. 이번 CLI 실행기는 읽기 전용 검토만 구현했으며 무인 쓰기 위임은 아직 실행·검증하지 않았다. 향후 쓰기 위임에는 별도의 허용 범위와 검증된 실행 경계가 필요하며 현재 Gemini 검토 프로젝트의 deny를 해제해 전용하지 않는다.

설치/로그인된 CLI가 현재 도구 계정에서 접근 가능해지면 주담당이 명령을 직접 실행한다. 현재처럼 권한 경계가 다르면 사용자가 일반 PowerShell에서 준비된 조사/프로브를 시작해야 한다. 매 작업의 모델 선택을 사용자에게 넘기는 규칙은 아니며, 권한을 우회하는 실행 브리지는 만들지 않는다. 계정 로그인·이용 한도/비용 변경·현재 대화 모델 설정·중요 위험 수용은 남은 사용자 조작이다.

## 검토·반영

일반 작은 수정은 필요한 자기 검증으로 진행할 수 있다. 구조·OS 경계·데이터 변경·릴리스는 독립 Gemini 검토를 권장한다. 실제 Gemini 접근이 없으면 ‘독립 검토 미실행’으로 남기며 가상의 의견을 만들지 않는다.

## STATUS·날짜별 기록

항상 읽는 문서는 STATUS와 관련 최신 기록, 현재 작업의 TASKS 항목이다. 작업에 필요한 구조·요구·규칙만 추가로 읽는다.

- STATUS: 현재 단계·목표, 완료/진행/검토 대기/막힘 ID, 담당·브랜치, 주요 오류/결정, 다음 작업·시작 조건, 마지막 KST 갱신 시각.
- 날짜별 `docs/work-log/YYYY-MM-DD.md`: 실제 수행 이력을 누적한다. 계획을 과거 완료 이력으로 소급 작성하지 않는다.
- **기본 단위는 기능 하나**다. 같은 기능의 여러 대화·조회·코드 수정·테스트를 묶어 구현과 검증을 마칠 때 STATUS·날짜 기록을 한 번 정리한다. 문서/환경 작업은 같은 목적의 작업 묶음을 한 단위로 한다. 작은 작업마다 새 기록 ID를 만들거나 Notion·push를 반복하지 않는다.
- 실제 중단·담당 인계·중요 범위/위험 결정 또는 사용자의 명시적 기록/백업 요청은 예외다. 이때 이어받는 데 필요한 상태·검증·남은 일만 한 번 남긴다. 단순한 도구 대기나 진행 안내를 중단으로 취급하지 않는다.
- 잘못된 기존 기록은 원문 사실을 숨기지 않고 정정 이유·시각을 남긴다.
- 커밋 전 ‘미커밋’ 허용. 기능 내 로컬 커밋은 필요할 때 작게 나누고, 기능 마무리의 기록·검증을 포함해 작업 브랜치를 한 번 push한다. 최종 해시나 Notion 성공 시각만 추가하려고 재커밋·재푸시하지 않는다. 이전 커밋 또는 브랜치·기록 ID로 찾고 최종 해시·동기화 결과는 Notion/최종 보고에서 연결한다.

```text
기록 ID: WL-YYYYMMDD-일련번호 / 작업 ID:
시작·종료 KST: 실제 확인 시각(모르면 미확인)
도구·CLI / 요청 모델·추론 / 실제 확인 모델·추론:
목적·실제 수행 내용:
수정 파일·이유:
브랜치 / 관련 커밋·PR(없으면 없음·미커밋):
검증 ID·방법·결과·근거:
오류·미완료·한계:
다른 AI 검토·채택 여부(미실행도 표시):
사용자 결정·변경 이유:
Notion 반영: 대기 | 실패(이유) | 재조회 확인
다음 담당에게 전달할 작업·시작 조건:
```

요청한 설정과 실제 표시를 분리한다. 실제 모델을 확인 못 하면 ‘미확인’으로 둔다. 대화 전문·터미널 전체·인증 정보·로그인 링크를 복사하지 않는다.

### 갱신 대상과 확인

대상은 [개발 현황·작업 기록](https://app.notion.com/p/3ee6817a2571813fb2dbe1f99ad69a59)이다. 기획·기존 일정 본문은 이번 작업에서 수정하지 않는다.

1. 기능 시작 때 최신 로컬 STATUS·최근 기록을 읽는다. Notion은 기능 마무리의 갱신 직전에 기존 페이지와 같은 작업/기록 ID를 확인하며, 작은 중간 작업마다 다시 조회하지 않는다.
2. 현재 수정 담당이 기능의 구현·검증 결과와 결정을 한 번 취합한다. 상세 계획 ROADMAP, 상세 작업 TASKS, 이력 work-log가 각각 기준이다.
3. 기능 마무리 때 Notion 진행판과 해당 기록을 한 번에 갱신한다. 전체 단계·실제 완료/검증·진행/막힘·다음 작업·결정·작업/기록 ID·확인된 Git 링크·상세 문서 위치만 요약한다. 실제 중단/인계 등의 예외는 위 기록 규칙을 따른다.
4. 업데이트 후 다시 읽어 대상 ID·내용·링크·누락을 확인해야 ‘동기화 확인’이다. 저장 응답만으로 완료 처리하지 않는다.
5. 실패하면 로컬에 ‘Notion 반영 대기’와 오류를 남긴다. 연결이 복구된 다음 기능 마무리 또는 사용자 동기화 요청 때 대기 기록을 함께 반영한다. 재시도 전 조회하여 이미 반영된 같은 기록 ID는 새로 만들지 않고 필요한 부분만 보완한다. Notion 실패를 일반 코드 작업의 시작 차단 조건으로 삼지 않는다.
6. 기존 기록·사용자 내용·하위 페이지를 보존한다. 다른 AI와 동시에 갱신하지 않는다.
7. Git 푸시가 실패하면 원격에 없는 커밋 링크를 작동하는 완료 링크로 제시하지 않는다. 로컬 해시·푸시 실패·브랜치 위치를 명시한다.

기존 Slack 알림은 예전 일정 페이지를 참조하는 것으로 기록되어 있다. 이번 요청으로 메시지를 보내거나 자동화 설정을 바꾸지 않는다. 변경 제안이 기존 알림에 반영됐다고 보장하지 않는다.
