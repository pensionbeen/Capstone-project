# T-011 기능별 Codex 대화

저장한 기능의 설명·완료 조건·버전·관련 경로를 Codex CLI에 전달하고, 실제 대화의 기능과 현재 선택한 기능을 구분한다. 분석·구현 계획을 제안하는 읽기 전용 연결이며 소스 자동 수정이나 기능 검증 완료는 아니다. 실제 검사와 실패 이력은 [작업 기록](work-log/2026-10-12.md), 분담은 [병렬 개발 기록](PARALLEL_DEVELOPMENT.md)을 따른다.

## 사용하는 순서

1. 실제 프로젝트 폴더를 선택하고 저장한 기능을 연다. 포함된 말단 기능을 선택한다. 예시 프로젝트·묶음·제외 기능은 실행할 수 없다.
2. 기능·파일 관리의 **기능 AI 대화 열기** 또는 작업 내용에서 같은 버튼을 누른다. **연결 준비 확인**으로 설치된 Codex와 기존 로그인을 확인한다.
3. 선택한 기능의 버전·완료 조건·관련 경로를 확인하고 **이 기능으로 대화 시작**을 누른다. 추가 요청은 선택 사항이다.
4. 정상 종료·정리된 같은 기능 문맥에서는 답변을 보낼 수 있다. 답변은 공백을 제외한 내용이 필요하고 최대 2,000자다.
5. 대화창을 닫거나 다른 화면·기능으로 이동해도 현재 실행은 유지된다. 대시보드의 **현재 대화 열기**로 돌아간다. 선택한 기능 B와 실제 대화 A가 다르면 두 문맥을 구분해 표시한다.
6. 실행 중에는 중단할 수 있다. 다른 기능이나 변경된 조건으로 이어가려면 기존 실행이 끝난 뒤 **이 기능으로 새 세션 시작**을 누른다. 일반 대화 전환도 명시적으로 새 대화를 만든다.

현재 세션 하나만 앱 메모리에 유지한다. 화면 이동은 대화를 지우지 않지만 앱 재시작 후 대화·활동 복원은 T-012 후속이다. 기능별로 여러 실행을 동시에 띄우는 기능은 없다. 개발 과정의 Codex 병렬 작업과 앱의 실행 개수를 혼동하지 않는다.

## 실행과 완료를 구분하는 규칙

- 실행 대시보드는 준비·실행·중단·종료·오류 등 관측 상태를 보여준다. 조회 실패도 별도로 표시한다.
- Codex가 종료하거나 “완료”라고 답해도 검증 DB와 진행률은 바뀌지 않는다. [수동 검증](VERIFICATION.md)에서 현재 완료 조건의 근거를 확인해야 한다.
- 기능을 수정하면 이전 출력에는 실행 당시 기능과 버전이 남는다. 기존 대화의 답변 버튼은 조건이 달라졌을 때 차단하고 새 세션을 안내한다.
- 실행·실행 요청 전달·기능 저장이 겹치지 않도록 화면과 main에서 검사한다. 실행 중 요구 변경안을 별도 보관하고 적용하는 절차는 T-013 후속이다.

## 공통 연결 계약

| 접점 | 계약 |
|---|---|
| `FeatureSessionContext` | `featureId`, `revision`, `title`, `description`, `criteria`, `relatedPaths` |
| `AISnapshot` | `purpose: 'feature'`, `featureContext`로 실제 실행 문맥을 전달 |
| `DesktopBridge.sendFeaturePrompt` | `projectId, action, featureId, expectedRevision, input, expectedOutputId, expectedRunId` |
| IPC / 인증 REST | `ai:feature` / `POST /v1/projects/:id/session/feature` |
| `action` | `start`는 새 대화, `answer`는 같은 문맥·대화 재개 |
| 식별자 | 기능 ID는 저장 항목, revision은 조건 버전, outputId는 대화 출력 묶음, runId는 매 전송의 실행 |

renderer는 실행 파일·명령·작업 폴더·기능 원문을 결정하지 않는다. main이 등록된 프로젝트와 SQLite의 실제 기능을 읽고, 포함된 말단인지와 버전을 검사한다. 비동기 경로 검사 전후 및 실행 드라이버 준비 뒤에도 기능 원문·경로·출력/실행 ID를 대조한다. 준비 중에는 실행 예약으로 다른 변경을 막는다.

관련 경로는 선택 프로젝트 안의 실제 상대 경로여야 한다. 없는 파일·바깥 경로·junction 등 링크를 거부하며, 목록이 비어 있으면 프로젝트 루트를 검사한다. 전체 문맥이 실행 입력 상한 8,000자를 넘으면 자르지 않고 오류를 알린다. 이 사전 검사는 이후 모든 OS 파일 접근을 추적하거나 차단하는 기능이 아니다.

같은 프로젝트에서 이전 runId의 중단 요청이 새 기능 준비 중 도착해도 새 준비를 취소하지 않는다. 아직 새 runId가 없는 준비 예약은 공개 중단 대상이 아니며 앱 종료만 직접 취소한다. 실제 활성 실행이 시작된 뒤의 중단은 기존 runId 검사와 정리 절차를 따른다.

## 연결 방식과 남은 범위

ORBIT → 제한된 preload/IPC → 인증된 앱 내부 REST/WS → 기존 PTY 호스트 → 설치된 **Codex CLI 0.162.1** 순서다. 기존 ChatGPT 로그인을 사용하며 앱에서 모델 API 키를 받아 직접 모델 API를 호출하지 않는다. 내부 REST API는 UI와 실행부를 연결하는 로컬 통신이다.

CLI 시작 헤더의 모델·작업 폴더·읽기 전용 설정과 실제 응답을 확인한다. CLI가 표시한 설정과 원격 모델 신원 인증은 다르다. 앱 Gemini 연결·여러 AI 동시 실행·대화형 TUI·자동 파일 수정은 이번 구현에 포함하지 않는다. [X-002 부분 조사](../experiments/x-002-file-access/RESULTS.md)의 실제 OS 보호는 미확인이며 T-014 통합은 차단 상태다.
