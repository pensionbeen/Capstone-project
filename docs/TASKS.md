# 실행 작업과 요구사항 추적

작업 정의의 기준 문서다. 날짜·전체 공수는 [ROADMAP](ROADMAP.md), 현재 상태는 [STATUS](STATUS.md), 실제 검증 결과는 날짜별 작업 기록에 둔다.

## 상태와 완료 기준

- 계획 → 진행 중 → 검증 대기 → 완료. 선행 조건·환경·결정이 없어 진행할 수 없으면 막힘으로 기록한다.
- 문서 완료·구현 확인·검증 완료·사용자 확인 완료는 각각 기록한다. 아래 계획 표가 채워졌다는 이유로 기능을 완료하지 않는다.
- 일반 작업은 명시한 조건과 실제 검증 결과로 완료 판단한다. 핵심 범위 변경·중요 위험 수용·최종 시연/제출 범위만 사용자 결정으로 남긴다.
- 실험은 성공/실패/미결 결과가 명확히 남으면 ‘조사 작업’은 끝날 수 있다. 제품 요구 충족은 해당 성공 검증과 실제 통합이 있어야 한다.
- 예상 공수는 1인 순작업 시간(h), 작업 자체의 확인·기록 포함. 기다리는 날은 포함하지 않는다. 8h를 넘는 작업은 착수 시 실험 환경/정상 경로/실패 검증 등 2~4h 단위로 나누며 범위와 합계를 유지한다. 장기 작업은 착수 전에 재추정한다.

## 증거를 남기는 최소 양식

```text
검증 ID / 작업 ID / 요구 ID:
대상 커밋·빌드 / 실행 환경·버전 / 수행 시각 KST:
방법·실험 데이터 / 기대 결과:
실제 결과: 통과 | 실패 | 미실행 | 일부 확인
근거: 재현 절차·필요한 출력 요약·파일/영상 위치
한계·남은 문제 / 기능 상태 / 사용자 결정이 필요한 경우:
```

증거 파일을 아직 만들지 않았으면 가짜 링크를 만들지 않는다. 실제 기록이 생기면 날짜별 work-log의 기록 ID와 연결한다. UI의 성공 표시·AI의 ‘완료’ 발언·프로세스 종료 코드는 단독 완료 증거가 아니다.
